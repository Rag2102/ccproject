About this project

A cloud-computing coursework project built into a working portfolio piece: a real decision policy over three learned/derived signals, deployed two different ways.

Cloud providers lose money two ways when a VM's underlying hardware is about to fail: wait too long and a customer's workload goes down; migrate too eagerly and you burn compute and network capacity you didn't need to. This project asks whether a mitigation policy that actually weighs failure probability, estimated time-to-failure, workload criticality, and the real cost of migrating beats the simpler industry-standard approach -- flag and migrate anything that crosses a fixed probability threshold, the same baseline Microsoft's Narya system was built to improve on.

The pipeline runs on two real, independently-sourced datasets -- Microsoft's Azure Public Dataset (2M+ real VMs over a 30-day trace) and Backblaze's published drive-failure telemetry (122K+ drives, ~6.9K real failures) -- since no public dataset links real VM placement to real hardware outcomes directly. A calibrated hazard model turns drive age and model into a failure probability and a time-to-failure estimate; a cost model prices live migration using the Clark et al. pre-copy formula against real VM memory/vCPU data; and a full historical replay simulation compares the two policies honestly, at a matched migration budget rather than a flattering one. The headline result: the two policies land close together under random workload placement, and the cost-sensitive policy's advantage shows up cleanly once workload criticality correlates with real hardware risk -- the realistic case, not the pessimistic one.

This page is the second of two deployments that share one prediction module, built to demonstrate a fully serverless cloud architecture: a static frontend on S3 + CloudFront (this page), a JSON API on API Gateway + Lambda (the model), and a Step Functions fan-out across independent Lambda workers for the correlation-sweep experiment above. The project's real findings precomputed, from the actual experiments

These numbers come from a full historical replay simulation and a follow-up correlation-sensitivity study over the real Backblaze + Azure datasets -- not from this demo's live calculator above.

MetricCost-sensitiveThreshold (matched budget)Threshold (naive, τ = 0.0073)

Under random workload placement the fair comparison is the matched-budget column: with nearly the same number of migrations (5,522 vs 5,116, the closest achievable match) the cost-sensitive policy costs about 3.1% more than the threshold policy. The naive column (τ = 0.0073, the 95th percentile of host risk) migrates far more and the cost-sensitive policy costs about 11.1% more than it, but that is not a like-for-like comparison. This is an honest, non-confirmatory baseline result; the follow-up experiment on the right shows where the hypothesis does hold.

Does a deep attention model beat the calibrated hazard model?

Both models scored on the identical held-out test rows -- including why a deep attention architecture doesn't beat a well-calibrated gradient-boosted model here.

The gradient-boosted hazard model wins on every metric, especially calibration -- consistent with the well-known finding that tree-based models tend to match or beat deep architectures on small-feature-count tabular problems, and a reminder that a fancier architecture doesn't automatically produce a usable probability.
