# Zhang et al., Deoxys: A Causal Inference Engine for Unhealthy Node Mitigation in Large-scale Cloud Infrastructure (SoCC 2024)

Source read: the arXiv copy (2410.17709v1, 19 pages), which carries the SoCC '24 header (Redmond, 20-22 Nov 2024; DOI 10.1145/3698038.3698534; proceedings pages 361-379 per Crossref). Read 28 Oct 2026: sections 1-5 (introduction, background, causal model, design, offline evaluation) and 8-10 (lessons and limitations, related work, conclusion) in full; sections 6-7 (online A/B results, extracted policies) skimmed.

| Field | Notes |
| --- | --- |
| Problem | *Reactive* mitigation: once a node has lost its heartbeat long enough to be marked unhealthy, choose **Reboot** (in place, no extra resources) or **Redeploy** (move every VM on the node elsewhere, which needs capacity), to minimise average VM downtime on that node (sections 2.1, 2.4). One binary decision per node per event. It does not predict failures; it acts after one. |
| Data | Microsoft production: one month of observational data from the legacy policy, 20,218 unhealthy events, each with diagnostic signals X (VM count and types, network status, error code, repeat count, uncorrectable-error tag), the action A and the node's average VM downtime Y (sections 2.3, 5.2). Times are normalised; no absolute numbers. |
| Baseline | Random; the legacy heuristic (wait a hardware-type-dependent time, Reboot, wait again, then Redeploy); Narya (bandit); NENYA (cascade RL); and four other DML estimators (sections 5.1, 5.4). No probability threshold and no budgeted comparator. |
| Metric | Average VM downtime per node (AVD, the objective) and Annual Interruption Rate (AIR, monitored, from Narya) (section 2.5). |
| Claim | Double machine learning with a causal forest (CauForeDML) estimates each event's individual treatment effect τ = E[Y(Redeploy) - Y(Reboot) given X] from observational data, so no action-level A/B test or online exploration is needed (section 3). In their own simulator built from historical events (not released): downtime 4.8 units against 5.6 for NENYA, 6.4 for Narya, 12.1 for random; Narya and NENYA need 136 and 1,350 events to converge, Deoxys none (Table 1). In production against the legacy policy: 53% lower average downtime, 49.5% lower AIR (abstract, section 6). |
| Design pieces that touch this project | **Policy fallback (section 4.2):** use the legacy policy when the ITE interval is wide (τ_upper - τ_lower ≥ ε) and the estimate is near zero (\|τ\| ≤ ξ). **Action override (section 4.3):** turn Redeploy into Reboot when the predicted saving \|τ\| is below a threshold ϖ set by a cost function of downtime against node resources (the formula is withheld for anonymisation); force Redeploy and mark the node unallocatable after repeated unhealthy events. **Sticky policy assignment** by hashing node ID (section 4.4). Weekly retraining (section 4.5). |
| Limitation | One operator; normalised units; simulator and data not released; ε, ξ, ϖ not given; the fallback is a per-event heuristic with no stated error rate; reactive only, and the authors name "when to act" as future work (section 8). No resource budget: capacity enters only through the override threshold. |
| What we reuse | (1) A second production precedent for "fall back when the model is unsure", which P6 must cite. (2) Their Table 1 is the only published head-to-head of Narya and NENYA, in a private simulator: it supports keeping P5 (Narya-inspired) as a serious baseline. (3) The sticky-assignment argument (node outcomes are not i.i.d. across consecutive events) matches our per-host pairing. |
| Reviewer would say | "Deoxys already has a guard that falls back to the existing policy when evidence is weak; what does P6 add?" Answer: Deoxys's fallback is a per-event rule on one model's interval width with unstated thresholds and no error control. P6 is a policy-level switch: a sequential test whose false-switch rate is bounded across repeated looks (α spent as 6α / (π² k²)), plus a calibration audit on realised outcomes, with a tuned threshold as the fallback, and it is tested on a pure-noise control under a pre-registered bar. Also, Deoxys is reactive (which action after a node is already unhealthy); this project is proactive (which VMs to move, under a GB budget, before a predicted failure). |
